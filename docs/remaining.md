## `ANALYZE` が `/ingest` 経路では一度も呼ばれない

`db.py: analyze()` を呼ぶのは `csv_import.import_all()` だけである。`events` は `/ingest`
経由でしか増えないため、**`events` テーブルの統計情報が更新される経路が存在しない。**

実機の DB（約 31 万件）で `sqlite_stat1` を見ると、`events` の統計行が 0 件だった
（`cost_daily` の 4 行分のみ）。結果、プランナが不適切なインデックスを選ぶ。実測で
207.6ms → `ANALYZE` 後 73.1ms、合成データでは 106.9ms → 3.3ms（約 35 倍）まで差が出た。
`ANALYZE` 自体の所要時間は実機で約 65ms であり、無視できるコストではない。

events が主体のシステムで、実質「`ANALYZE` 運用なし」の状態が続いている。

**完了条件** — `/ingest` の受信処理（一定件数ごと、または一定間隔ごと）から `analyze()` を
呼ぶよう見直し、`events` の統計情報が `/ingest` 経由でも更新されることをテストで固定する。
即時 `ANALYZE` が受信のレイテンシを悪化させる場合は、非同期化や間引きを設計判断として
`decisions.md` に記録する。
