## 1. アーキテクチャ上の判断

| # | 論点 | 採った案 | 採らなかった案と理由 |
| --- | --- | --- | --- |
| 1 | サーバの数 | **1 プロセス** | *ガバナンスとログで 2 分割* — 配信が git である以上ガバナンス側にサーバ機能がほぼ無く、効果測定は 3 テーブルの突合。分けるとプロセス間結合という要件にない問題が生まれる |

| 10 | 集計の実行場所 | **SQL の `GROUP BY`** | *アプリ側での全走査* — 行数に線形なメモリと応答時間。イベントスタディの畳み込みのみ、集計後の数千行に対してアプリ側で行う |
| 11 | フロントエンド | **素の HTML + CSS** | *チャートライブラリ* — CDN 到達性が不明で、表と棒で判断には足りる |
| 12 | 監視 | **概況画面の健全性 1 行** | *アラート・通知・定期実行の監視* — 日次で見る画面に 1 行あれば気づける |
| 13 | CSV 取込の起動 | **画面のボタン** | *定期実行* — 実行基盤に仕組みが無い。日次 1 クリックが最も正直で最小 |
| 14 | コンテナ化 | **Dockerfile 1 枚** | *マニフェスト一式* — 現時点で必要がなく、起動コマンドが同じである以上、移行時に書けばよい |

## 2. 実装

### `app.py` は import 時に `db.init()` を呼ぶ

起動時に契約と実テーブルを突き合わせて落ちることが、この設計の関門そのものである。
テストのための遅延初期化フラグを作ると、その関門がテストの都合で緩む。
テスト側が接続先を設定してから `app` を import する。

### トークンの比較は `hmac.compare_digest` をバイト列で行い、両辺の符号化方式が違う

| 値 | 復号のされ方 | 元のバイトを取り戻す符号化 |
| --- | --- | --- |
| リクエストヘッダ | WSGI が **latin-1** で復号する | `latin-1` |
| 環境変数 | `os.environ` が **utf-8 / surrogateescape** で復号する | `utf-8` |

両辺を同じ符号化で揃えると、ヘッダ側だけが二重に符号化され、非 ASCII のトークンが
永久に一致しない。運用者が全角文字や貼り付け由来の NBSP を含むトークンを設定すると、
正しいトークンを送っている全端末の受信が恒久的に失敗する。

`str` 同士の `compare_digest` は ASCII 以外で `TypeError` を送出するため、バイト列で
比較する。片側の符号化を揃えると、非 ASCII のトークンが壊れる。

**この欠陥は `test_client()` では検出できない。** Flask の `test_client()` はヘッダを
復号済みの文字列としてそのまま渡し、WSGI の latin-1 による線上の符号化を経由しない。
検査は WSGI 環境を直接組むか実サーバで行う。

### サブパスのラッパは 1 個だけ置き、剥がした結果が空文字なら `/` に寄せる

`PATH_INFO` が公開サブパスと完全一致すると、剥がした結果が空文字になり、Werkzeug が
`/` へリダイレクトする。公開サブパスそのものは利用者が最初に叩く URL であり、末尾
スラッシュだけが違う URL を作らない。末尾スラッシュ付きの設定値を与えたときの
自己リダイレクトのループも、同じ 1 行で消える。

ラッパを増やすと、前段がサブパスを剥がすか剥がさないかに依存する分岐が生まれる。

### `db.q()` は SQL の文字列リテラル中の `?` も置換する

方言の分岐を `db.py` 1 ファイルに閉じるための割り切りである。そのため、
`LIKE '%?%'` のような `?` を含む文字列リテラルを SQL に書かない。書くと、MySQL 接続時
にプレースホルダとして解釈されて壊れる。この前提を強制する検査は持たない。置くとすれば
SQL を構文解析する必要があり、`db.py` を 1 ファイルに閉じる目的と釣り合わない。

### CSV 取込は 1 ファイルの失敗で全体を止めない

取込ボタンは 1 つであり、押すたびに取込ディレクトリの全ファイルを取り直す。この
ディレクトリには AI Gateway 以外の CSV が実際に置かれており、必須列を持たない 1 本で
走査全体が落ちると、コストの CSV が 1 行も入らない。失敗したファイルは取込結果の画面に
失敗として表示するので、気づく手段は残る。

捕まえる例外は `ValueError`（必須列の欠落）・`OSError`（権限等で読めない）・
`csv.Error`（CSV として壊れている）の 3 つに限る。`except Exception` へ広げると、
実装のバグ（`AttributeError` / `TypeError` / `KeyError`）まで「ファイル起因の失敗」
として握り込まれ、区別が付かなくなる。

### CSV は `encoding="utf-8-sig"` で読む

BOM 付きの CSV は先頭ヘッダが `﻿Date` になり、「必須列が欠けている」として全行が
捨てられる。AI Gateway の CSV を Excel 経由で再出力すると BOM が付きうる。
`utf-8-sig` は BOM 無しのファイルもそのまま読める。

### 集計の `SUM` は `COALESCE(..., 0)` で包む

AI Gateway の CSV は `Cost` 欄が空のセルを含む。NULL のまま合計すると、その 1 セルの
ために効果測定の画面全体が 500 になる。

### 利用状況の集計は結合ではなく条件付き集約 1 本で書く

結合列に NULL を含む行（`command_source` が NULL のスラッシュコマンドなど）は
`NULL = NULL` で結合に失敗し、実際には使われているものが「0 回・0 人」として出る。
積極的に嘘をつく形である。

### 画面は NULL を「未設定」「—」と表示する

`prev_value` が NULL になるのはキーを持たない端末であり、初回適用時は全端末がこれに
当たる。そのまま描画すると、運用開始直後の適用状況画面がほぼ全行 `None` で埋まる。

### インデックス名は `ix_<テーブル名>_<列を _ で連結>` とする

列の並びから一意に決まる名前であれば、定義とインデックス名がずれない。最長のものでも
MySQL の識別子上限（64 文字）に収まる。別の命名に変えると、既存の DB に古い名前の
インデックスが残る。

### 本番の依存は 11 パッケージを `==` で固定する

毎起動 `pip install` が走る基盤では、固定しないと「同じコードのまま、再起動しただけで
別のバージョンが走る」状態になる。上流の任意のリリースが、こちらの操作を伴わずに本番を
止めうる。

`pip download --python-version` は環境マーカー（`python_version < '3.10'`）を指定した版
ではなく**実行中のインタプリタ**で評価するため、Flask が 3.9 でのみ要求する
`importlib-metadata` と、その依存の `zipp` を静かに落とす。9 パッケージで固定すると、
基盤の 3.9 上での install がこの 2 つを固定されていない版で引き込み、依存固定の目的が
崩れる。3.10 以降へ上げるときは、この 2 行が不要になる。

## 3. 受け入れている限界

直せば変わるが、今は直していないものである。

### 同一の `ts` を持つ行のタイブレークが定義されていない

「最後に観測した値」は `ts` の降順で 1 行を選ぶ。同じ `ts` の行が複数あるとき、どれが
選ばれるかは決まっていない。秒単位の `ts` で同着が起きるのは、同じ端末が 1 秒以内に
2 回書いた場合に限られ、そのとき両者の値は実質的に同じである。順序を決めるには第 2 の
整列キーが要り、そのキーは全経路で単調増加であることを保証しなければならない。定義を
足すと、その保証の維持がすべての書き込み経路に乗る。

### 版の分布は、参照キーの行を持たない端末を落とす

版の分布は特定のポリシー項目の行から取る。その項目の行を持たない端末は分布に現れない。
ポリシーの全項目は同時に記録されるため、欠ける端末は運用では生じない。MySQL では同着時
の並び順も不定である。全項目を横断して端末を数える形に変えると、集計が項目数に比例して
重くなる。

### コンテキスト量の分布は準拠者 1 人につき 1 クエリを発行する

利用者数に比例してクエリ数が増える。140 名規模では画面の応答に影響しない。1 本の SQL
にまとめるには利用者ごとの分位を DB 側で出す必要があり、方言差の出る構文に踏み込む
ことになる。方言に依存しない方針と引き換えになる。

### 取込ディレクトリが未設定のとき、取込は静かに「0 件成功」になる

未設定を失敗として扱わず、対象 0 件として正常終了する。起動スクリプトと Dockerfile が
必ず設定するため、運用でこの経路は通らない。未設定を失敗にすると、CSV を使わない構成で
サーバが起動できなくなる。

### 取込に失敗したファイルの文言には、ファイルの絶対パスが含まれる

その文字列はそのまま画面に出る。画面は Ingress 認証の内側にある。パスを伏せると、
どのファイルが失敗したかを運用者が特定できず、取込結果の画面が気づく手段として機能
しなくなる。

## 4. 採らないと決めたこと

- **群の割り当てを使った統計的な検定を行わない。** 効果測定の画面が出すのは相対日の
  傾きであり、因果効果ではない
- **監視・アラートを持たない。** デプロイログの確認で足りる規模である
- **負荷試験・スケールアウトを行わない。** SQLite 運用ではスケールアウトできない
- **Kubernetes への移行手順を持たない。** `Dockerfile` を用意するところまでである

### 採らないが、条件が変われば再検討すること

| 選択肢 | 何が変わるか | 再検討の条件 |
| --- | --- | --- |
| MySQL 側の `ANALYZE TABLE` と索引の見直し | SQLite では `ANALYZE` の有無で 10 倍以上の差が出た。InnoDB では skip-scan の可否も統計の要否も別問題である | MySQL を本番に選び、画面が遅いと感じたとき |
| データの保持期間 | 年間 1,500 万行で DB は 6 GiB を超える見積もりである | ディスクが逼迫したとき、または窓を跨いだ集計が遅くなったとき |
